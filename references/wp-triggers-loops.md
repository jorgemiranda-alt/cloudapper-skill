# Workflow patterns: triggers, order, loops and batching

Entries headed `WP-0xx` use the format and statuses explained at the top of `workflow-patterns.md`; `wp-index.md` lists every entry.

## 1. Triggers and order

### WP-001 A workflow's record change only triggers workflows later in the list
**Rule:** Place a workflow that creates or updates records **before** every workflow it should trigger (lower Sequence). Keep the list order identical between environments.
**Why:** A change made by a workflow only triggers workflows with a higher Sequence. A workflow cannot retrigger itself.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: a batch workflow placed after the workflow it should trigger fired nothing; moved before it, everything fired. Re-check from another app's execution logs: each forward link of a three-step chain fired within seconds (21, 20, then 54 and 54 runs), and a later workflow's updates to a form added no runs to an earlier workflow triggered on that form (54 runs each).

### WP-002 Setting a status to its current value triggers nothing
**Rule:** To rerun a record that already has the trigger value, set an intermediate value first ("Pending"), or route: "Pending" if currently "Running", else "Running".
**Why:** `Status _IsUpdated` only fires when the value actually changes.
**Status:** Observed · baseline · Evidence: a record at "Running" set to "Running" again did not start its workflow.

### WP-003 Status-driven pipeline
**Rule:** Buttons set Status (ActivityType 1); After-edit workflows trigger on `Status _IsUpdated AND Status = X`. Never let a workflow write the status that triggers itself.
**Caveats:** Before changing a status by hand, list every workflow triggered on that field.
**Status:** Observed · baseline

### WP-004 Re-creating a record re-runs its On Create chain
**Rule:** Before re-creating a record (to fix or rerun it), list the On Create workflows of its form and expect all of them to run again.
**Status:** Observed · baseline

## 2. Loops and batching

### WP-005 Triggered runs of one workflow are serial, and the caller doesn't always wait
**Rule:** Run one batch at a time; check the triggered records' statuses before starting another batch.
**Why:** Triggered runs of one workflow execute one at a time. Some CREATE/UPDATE steps wait for the workflows they trigger (the parent lasts exactly as long as its child); others only queue them.
**Caveats:** Not every trigger is serial: runs of a workflow on an "After Async … On Create Or Update" trigger overlapped (a second run started while the first was still running). Don't rely on one-at-a-time order for async triggers; make each run safe to run alongside another.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: a loop that updated 24 records finished in seconds while the 24 triggered runs executed one by one over the next hour; a second batch started meanwhile lost its triggered runs. Re-check from another app's execution logs: 25 of 54 runs of an async-triggered workflow started before the previous run ended (runs of 1.6–22 s); 408 runs of a non-async After Create workflow never overlapped.

### WP-006 A FOREACH iterates its list as fetched
**Rule:** Delete in one bulk step first, then fetch and loop. Never delete records inside the loop that iterates them.
**Why:** Records deleted inside a FOREACH are still iterated and counted, then fail to update ("No record found to update").
**Status:** Observed · baseline · Evidence: seen on a live app.

### WP-007 Batch rerun from a parent record
**Rule:** To rerun every child process of a period or group from one click:
- Child form under the parent (Confirm, Reason, read-only Batch Status) + parent button (UI workflow `ADD_NEW_RECORD`, Parent = `_triggerForm`); grant the role privilege and save the relation.
- Workflow on the batch form (create): mark In Progress → load the parent → LOOKUP_RECORDS the children (scope filters, sorted so related items run together) → FOREACH → ROUTER on current status → UPDATE status (WP-002) → after the loop mark Completed.
**Caveats:** Place it before the workflow it triggers (WP-001). Sort so items sharing data run consecutively, so WP-010 kicks in. Mind WP-005.
**Status:** Observed · baseline

### WP-008 Run stamp + bulk cleanup for safe reruns
**Rule:** Set `Date&Time = UtcNow()` at the start, stamp every record the run writes with it, and delete records of the same scope with an older stamp in one step before reading them back.
**Status:** Observed · baseline

### WP-060 Process records in date order without a sorted lookup: a WHILE day loop
**Rule:** When rows must be handled oldest first (for example grouping consecutive days) and no sort format is known for `LOOKUP_RECORDS` (`filterSorting` has only been seen empty), loop over the days instead: a `WHILE` iterator on a number variable (`dayIndex <= N`), set a date-time variable to that day at the start of each pass, fetch only that day's rows (`>= day` and `<= day` on the date field), and handle them in an inner iterator. Increment the counter in the node that sets the day, at the start of the pass (WP-062 caveat), not after the inner iterator. Group by looking back: fetch earlier rows of the same person within a bounded range and count the rows in between (for example scheduled days) instead of asking for "the previous row".
**Why:** The order of an unsorted lookup is not defined, so a running group built on it can split or double. One pass per day makes the order explicit.
**Caveats:** Build each argument once and reuse the same object in both the expression and its `Arguments` (a helper that creates a new argument on every call gives an expression that names an argument that is not declared; the validator reports `UNDECLARED_ARG`). A lookback range limits groups to that range; a group that starts before the first day of the window is split.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: a 37-node workflow built this way passed `validate-workflows.js` with 0 errors and 84 expressions accepted by the editor check, including `DateTime.Parse(...)` and `.ToString("dddd")`; after the owner's edits it ran several times, status OK, and created three absence occurrences: one from 10-13 to 11-03 over consecutive scheduled days, with the excused holiday on 10-12 correctly excluded, and a lag date of 5 days.

### WP-062 Mark each source row processed, filter by reference fields, and count the loop at its start
**Rule:** (1) Give the source form a **Processing Status** field (`Pending` or empty, `Completed`). The workflow fetches only rows that are `Pending` or `isEmpty` and sets `Completed` with an `UPDATE_RECORD` (`id` = the iterated record) after handling each row. A row is then handled once even if the run is repeated, stopped or limited. (2) When the source row already carries a reference to the employee, filter other lookups on that reference (`Field` = the reference field of the target form, `ControlType 12`, `DataType 1`, value = the iterated record's reference field with `ControlType 12`) instead of a lookup per row by person number. (3) In a WHILE day loop put the counter increment in the first node of the pass. Never put a step that must always run after an iterator, a lookup that can return nothing, or a route that may not be taken.
**Why:** A "covered by an existing row" check does not tell a handled row from an unhandled one when several source rows map to one target row. The per-row employee lookup costs a call per row. A node placed after an iterator does not run when that iterator finds no rows ("No records found to iterate."), so a loop counter, a flag reset or any step that must always run cannot go there: it stops the loop from advancing and it runs to its maximum.
**Caveats:** Reference filters need the reference field filled: run the linking workflow first (WP-029). The owner confirmed that the counter placed after the inner iterator was the main fault of the first build: with no rows to iterate, the nodes after the iterator did not run, the counter did not advance, and the loop did not move to the next day. The run log shows "No records found to iterate." at warning level, status OK, so the failure is silent. A first run limited to one row per pass (`filterMaxRowCount: 1`) processes one row per day per run.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: owner's edited version ran with these changes: 51 of 75 source rows `Completed`, 24 still pending, three target rows created with the reference filled.

### WP-063 Rolling-window rule engine from child rows: day loop, pool sum, create-or-update state, consume
**Rule:** To apply a "points inside a window reach a threshold" rule to rows that may arrive in any order: (1) a WHILE day loop oldest first (WP-060, counter in the first node, WP-062) that fetches that day's eligible rows (status open, counts, past the lag date: `eligible date <= today`); (2) per row, look up the rule parameters (threshold, window days, cap) by a text code, not a reference; (3) set the window length and start in two assign nodes, then fetch the **pool** (same owner and code, open, window start <= date <= this row's date) and sum its points with an iterator and a number variable; (4) a route `sum >= threshold` leads to a lookup of the owner's state row by text keys (add a text code field to the state form) and a router with two exclusive routes: no state row (create it at the new level, then the ledger row) and state row present (a second router: below the cap, update state, create the ledger row, then consume; at the cap, create a review item and mark the row consumed); (5) consume = an iterator over the same pool lookup with an update that sets the consumed status and the ledger reference.
**Why:** Order is explicit, the sum and the consume use one pool so what was counted is what is consumed, and every create that needs a reference to a record made earlier in the chain is a child of that node. The ledger form requires its state reference, so the state row must exist first.
**Caveats:** Filters on a status dropdown should accept both the choice key and any older spelling already stored (an OR group). A pool that cannot be empty (it contains the row itself) is the only case where the threshold route may be a sibling of the sum iterator; otherwise place it differently (WP-062). Whether a created record's id can be used as a reference by later nodes of the same run is unconfirmed until the first run.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: run on test data (two Absence occurrences 14 days apart, 1.0 point each): the pool reached 2.0 and the run created the state row (Level 1), one Level Changes row (0 to 1, dated the second occurrence, snapshot "Points 2 >= 2 within 30 days") and marked both occurrences Consumed; every reference (state, source occurrence, person, track, consumed-by) was set, so the id of a record created earlier in the chain works as a reference for later nodes. Built first as a 31-node workflow that passed `validate-workflows.js` with 0 errors and 78 expressions accepted by the editor check; not run.

### WP-064 One recompute workflow fed by a queue: phases inside a WHILE loop, enqueue workflows that only add rows
**Rule:** Keep one workflow as the only writer of a ledger and its state. (1) A queue form (owner, code, From Date, reason, status Pending/Running/Done/Failed). Small enqueue workflows (After Create on the source rows; After Update on a flag with `_IsUpdated` and `= true`) only create a Pending row, or move an existing Pending row's From Date back when the new date is earlier (lookup Pending row by text keys, then two exclusive routes). (2) The recompute fetches Pending rows, and per row runs a WHILE loop whose first node sets the day and the counter; a router at the top of the body has exclusive routes: **Prepare pass** (counter = 1: count the anchor, supersede ledger rows from From Date on, reopen the rows they consumed, reset the state), **Day pass** (replay one day) and **Last pass** (mark the row Done). (3) Never delete ledger rows: mark them Superseded with a status field and filter active rows with an OR group (`Active` or `isEmpty`). (4) Builders that skip work already covered by a row must ignore Superseded rows, or a rebuild after an excuse finds the old row and does nothing.
**Why:** Triggers fire one run per row and runs overlap (WP-005), so a trigger that computes levels can race with itself. A queue makes the recompute run once per owner, in order, with a visible status. Putting the prepare, replay and finish steps in routes of an always-running loop avoids steps that follow an iterator that may find no rows (WP-062).
**Caveats:** The anchor level is the count of active increases before From Date, which holds only while levels move by +1 and no reductions exist; use the latest active row's To Level once reductions are built. Rows left Running by a failed run are not retried yet. Excused rows removed by a sync's stale cleanup are not detected by an update trigger.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: records created and updated through the records API fired the After Create and After Update enqueue workflows (the update trigger with `_IsUpdated` and `= true` fired once); an excused exception superseded its occurrence, queued a recompute and set 15 exceptions back to Pending; the recompute then superseded the Level Changes row (not deleted), reset the state to Level 0 and reopened the consumed occurrence, and the superseded occurrence stayed superseded (the reopen lookup must filter status Consumed). Two defects found in that test (the reopen left the consumed-by reference and the reset left the old last-increase date) were fixed and verified in a second cycle (WP-066). Built first as a 53-node recompute workflow and two enqueue workflows that passed `validate-workflows.js` with 0 errors and 248 expressions accepted by the editor check (with the occurrence builder); first run (one queue row, one employee, 22 days): status OK in 12 s; the row went Pending -> Running -> Done; the WHILE loop ended after the last day (the counter in the first node and `Math.Floor(({0} - {1}).TotalDays)` worked); the Prepare pass counted 0 earlier levels and, with no state row, skipped the reset; the Day pass pooled the 1.0 point occurrence and took no escalation below the 2.0 threshold. Escalation, supersede and the excuse enqueuer are not yet run.

### WP-065 A workflow description holds at most 1,000 characters
**Rule:** Keep `Description` under 1,000 characters when you create or update a workflow through the API; put the longer explanation in the project documentation.
**Why:** A longer text makes the save fail with HTTP 500 "22001: value too long for type character varying(1000)", and nothing else points to the field.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: an update with a 1,300-character description returned that error; the same workflow saved with 789 characters.

### WP-066 Clear a field in an update node: `null` for plain fields, an empty lookup's id for a reference
**Rule:** To empty a field in `UPDATE_RECORD`, assign the expression `null` (`{Expression: "null", Arguments: []}`) to a text, number or date field. A `null` on a **reference** field clears only its display text: the record keeps `<field>ReferenceId` and `<field>ReferenceTypeId`. To clear a reference completely, add a `LOOKUP_RECORD` of the referenced form with a filter that matches nothing (for example a status equal to a value that does not exist) before the update, and assign the reference from that lookup's `id` (`Field: "id"`, `FieldNodeId` = the lookup node, `ControlType 12`, `DataType 1` on the assignment).
**Why:** No saved node in the app showed a clear, so the format was tested: both forms passed the editor check, but only the empty-lookup form removed the reference id and type.
**Caveats:** Read the record back (`Records/fetch`) and check all three keys of a reference. A stale reference id is harmless only if every lookup that uses it also filters on the status that says it applies.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: a state's date field read back empty after a `null` assignment; a reopened row had text, id and type all empty after the empty-lookup assignment; with `null` alone the id and type stayed.

### WP-067 Use the trigger record's fields before adding a lookup, and match and copy by reference
**Rule:** Before adding a `LOOKUP_RECORD`, check whether the trigger record (or a node already in the tree) has the value you need. If the trigger form has a reference to the record you would look up, use that reference directly; do not look the record up again by a code or name. When a form has both a reference and a plain copy of the same thing (Person Id and Person Number, Track and Track Code), filter and assign with the **reference**. Copy a reference with an argument on the trigger's reference field: `Field: "<field>"`, `FieldNodeId: "__TRIGGERRECORD.<referencedFormId>.<field>"`, `NodeId: "__TRIGGERRECORD"`, `ControlType 12`, `DataType 1`. In a filter rule on a reference field, set `FieldNodeId` to `<lookupNodeId>.<referencedFormId>.<field>` with `ControlType 12` and `DataType 0`, and pass the same kind of argument as the value.
**Why:** A lookup the trigger already answers costs a query on every run and adds a node that can fail or match the wrong row. A code or name can be renamed or duplicated, but a reference points to one record id.
**Caveats:** Keep the plain copy only when a reader or a report needs it as text. Before relying on a trigger reference, check that the workflow that creates the record always fills it.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: the product owner corrected an enqueue workflow that looked up a track by its code although the triggering record already referenced it. The lookup was removed, the queue row's Track was copied from the trigger, and the pending-row filter changed from Person Number and Track Code to the Person Id and Track references.

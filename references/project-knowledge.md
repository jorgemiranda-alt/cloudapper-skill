# Project knowledge: requirements graph and app graph

Every project has requirements (an SRS, BRD, journeys, decision notes, or several documents) that change over time, plus a CloudApper app that is built against them. Keep **two graphs** current so Claude can see both what is required and what is built, and can compare them.

## Folder structure

```
<project>/
  CLAUDE.md                     entry point: where each fact lives, which source wins
  requirements/
    SOURCES.md                  one row per source document: name, link/ID, version, source last-modified, date fetched, status (current/superseded)
    sources/                    untouched originals or exports, one file per version: <doc>-v0.01.docx (add a new file for a new version, never overwrite)
    text/                       generated: the current version as Markdown, split by top-level section: <doc>-part1.md ... (stable names)
    graphify-out/               generated: requirements graph (graph.json, graph.html, GRAPH_REPORT.md, cache, manifest)
    CHANGES.md                  newest first: date, document, version, what changed in requirements (IDs added, changed, retired), decisions, open items closed
  app-export/<app>/             generated by the app export (WP-045): SUMMARY.md, app.json, form__*.json, wf__*.json, graph.json  (app graph)
  app-backup/                   dated backups taken before edits
  docs/<app-slug>/              app documentation (documentation.md)
```

Run graphify from inside `requirements/` (`graphify-out` is created in the current folder, so the two graphs never mix). The app graph stays in `app-export/<app>/graph.json`.

## The two graphs

| Graph | Built from | Answers | Built how |
|---|---|---|---|
| Requirements | `requirements/text/` | what is required, which rule/decision/open item relates to which, which tests cover what | `/graphify` on `requirements/text` (semantic: costs tokens) |
| App | the live app (forms, workflows, menus, roles) | what the app has, what triggers or writes a form, order problems | app export (WP-045): exact, free, no model |

Neither graph is a source of truth. The source documents win for requirement text; the live app wins for what is built. A graph is a map: use it to find the place, then read the text or the export file before stating a detail. Extraction groups requirement IDs into families (for example "FR-X-01..18"), so per-ID questions (does BR-12 have a test, what is the status of FR-X-04) are answered from the document's own tables (grep `requirements/text/`), not from the graph.

## Staleness: when to refresh

Check at the start of each session on the project, and again before any build or review that depends on a requirement:

1. **Requirements:** compare each current row in `SOURCES.md` with the source (Drive/Confluence modified time or version in the title). If the source is newer than `date fetched`, or a new version file exists, refresh. If the source can't be reached, say so and tell the user the graph may be out of date.
2. **App:** run the export's freshness check (`since`, WP-045). Re-export after every saved change.
3. After a meeting or decision changes a requirement, record it in `CHANGES.md` the same day, even before the document is revised, labelled "decided, not yet in document".

## Refresh procedure (requirements)

1. Fetch the new version. Save the original to `sources/` under a new version name; mark the old row in `SOURCES.md` superseded.
2. Convert to Markdown and split by top-level section into `text/` using the **same file names** as before. Stable names let graphify's cache reuse unchanged sections. If the section count changes, rename deliberately and say so.
3. Run `/graphify <requirements/text> --update` (full rebuild with `--force` only after deleting or merging files).
4. Diff the old and new text for IDs (BR, FR, NFR, OI, DEC, UAT): list added, changed and retired, and write them to `CHANGES.md`. A changed requirement may affect built workflows: compare with the app (below) and tell the user.
5. Update `SOURCES.md` with the version, source modified time and today's date.

## Answering and comparing

- Label every requirement statement with the status the document gives it (for example Confirmed, Proposed, Open) and the version and date. Never present a proposed or open item as decided.
- To compare requirements with the app: take the requirement's rule, find the workflows and forms in the app graph (`graphify query ... --graph app-export/<app>/graph.json`), then read those workflow files. Report gaps both ways: requirements with nothing built, and built logic with no requirement.
- Put requirement IDs (BR/FR) in a workflow's description (limit: 1,000 characters, WP-065) when you build or change it, so a text search links the app to the requirements.
- Both graphs may be wrong or incomplete (weakly connected nodes, inferred edges). Quote the source line, not just the graph, when the answer matters.

## Rules

- Never edit the originals in `sources/`. Never put credentials in any of these folders.
- Treat all of it as customer data: keep it in the project, not in this skill.
- Ask before running a semantic graph build over a large folder (it runs the model over every file); a refresh with `--update` only re-reads changed sections.
- If the project already has its own `CLAUDE.md` rules about which source wins, follow those and keep this structure as the default for anything they don't cover.

# CloudApper API: forms, relations, privileges, menus, UI workflows

Hosts depend on the cluster (see platform-model.md §1). Below, `API` = `https://<cluster>-api.cloudapper.com/api/`, `DAPI` = `https://<cluster>-designapi.cloudapper.com/api/` (or `api-design-cl2...`), `RAPI` = `https://<cluster>-reportapi.cloudapper.com/api/v3/`.

Auth headers and big-int `Version` handling: `api-reference.md` §1.
Entries headed `WP-0xx` use the format and statuses explained at the top of `workflow-patterns.md`; `wp-index.md` lists every entry.

## 4. Forms (design API)

- `POST DAPI EntityType/SaveEntityType` → create/update a form (top-level or child). Body = the designer's full form definition (`AllFields` in design format, `EntityTypeID`, `GlobalTypeID`, `Tittle` [sic], `IsEdit`, `Version` (string), `Client`, `ParentSchemas`, `ChildSchemas`, `CustomActionsConfiguration`, settings). New form: `IsEdit:false`, `Version:"0"`, your own GUID as EntityTypeID. Update: `IsEdit:true` + live Version.
  - Easiest reliable way to get a valid body: open the form in the designer, click Save with the request **blocked** (`route.abort`), keep `postData()`. See playwright-efficiency.md "capture" and "save-swap".

### WP-028 Add a field to a form by replaying the designer's save
**Superseded for new work:** use WP-071 (design API only, no designer capture). Kept for reference.
**Rule:** Capture the designer's own save body (above), add a copy of an existing field of the same control type with a new internal name, label and sequence, raise `StringFieldLastIndex` (or the matching counter), and send it with the raw live `Version`. Don't drag controls from automation.
**Why:** Drag and drop in the designer is unreliable from automation; a saved form body is a reliable source of a valid field definition.
**Caveats:** Send the replayed save through a frame without your interceptor, or the interceptor swallows it. The runtime may not show the field until **Reload App** (platform-model.md, caching). Check the client ID before writing. A whole new form: WP-043.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: a choice field added to a form, present in the app details and shown on the form after Reload App.

### WP-043 Build a whole form through the API from templates captured in the designer
**Superseded for new work:** use WP-071 (design API only, no designer capture). Kept for reference.
**Rule:** Create the shell in the designer and save it with one field (the designer won't save an empty form). Capture each needed save body without sending it: hook XHR/fetch `send`, keep the body, abort. Capture one form per control type you need (Form reference 12, Date 11, Date & Time 3, Text 4, Text area 5, Dropdown 2, Yes/No 1, Attachment 37). Build `AllFields` = Section, column, your cloned fields, then the system fields (ControlType 99). Per clone: replace the template's old `Name` everywhere in it with `<type>FieldN`, set `Label`, `Hint`, `Mandatory`, `SequenceNumber`/`TabIndex`/`DisplayNumber`, and the platform-0 `SequenceNumber` inside `StyleSettings`/`StyleConfiguration`. Form fields also need `ReferenceTypeID`, `EntityTypeID` and `ReferenceTypeId` set to the target form. Dropdowns need `DefaultValue` (`dro_choice_n` ids), `DefaultItems` and `colorOptions`. Set each `*FieldLastIndex` to the number of fields of that category (Date and Date & Time share the date counter). Check `ClientId`, `AppId`, `EntityTypeID` and `Tittle` against the target, POST with the captured live `Version`, then reload the designer and read the fields back.
**Why:** Two forms of one app differ only in title, description, ids, version, create date and the counters; the designer's own body is a valid template for every field.
**Dropdown choices:** build every dropdown with key = display text: `DefaultItems` `{"Open":"Open"}`, `colorOptions[].choiceId` the same text, `DefaultValue` the keys joined by commas. Do not generate `dro_choice_N` keys (WP-061).
**Caveats:** Send from a page without your hook (WP-028). The captured headers hold the bearer token: keep them in memory or session storage only, never print them, delete them afterwards. A capture that is aborted leaves the live `Version` unchanged, a sent one raises it.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: two forms (9 and 6 fields, with two dropdowns, form references and date-times) saved with `IsSaved: true`, reopened in the designer with every field, required flag and dropdown choice intact.

### WP-055 Hide, make read-only or require a field depending on other fields of the same record
**Rule:** Add an `AdvancedSettings` item to the field in the form body (WP-028): `{Id:<new GUID>, Title, Permissions:[{PermissionType:2, PermittedId:""}], FilterConfiguration:{Condition:"OR"|"AND", Rules:[{Field:<internal name of the controlling field>, Operator:"=", Value:<stored value>}]}, Properties:[{PropertyName:"HiddenInUI", Value:"Create,Edit,View"}]}`. The properties apply while the filter matches; other properties seen: `ReadOnly` (modes, empty = editable) and `ShowException` (error text for a mandatory-when-visible rule). Rules can nest (`{Condition, Rules}`). To hide a field for some values, list those values with OR.
**Why:** The runtime evaluates the filter against the record's own field values, so one field can drive what applies on each record (for example a track code deciding which rule fields show).
**Caveats:** Operators seen: `=`, `isEmpty`, `isNotEmpty`, `contains`; no "not equal" was seen. For a dropdown, check what the rows really store before choosing the value to compare (WP-061): a workflow filter on a dropdown matches the stored choice key, and the label does not. Open browsers show the old form until **Reload App** (platform fact 5).
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: three fields on one form hidden by a code field; after Reload App a record with another code no longer showed them, a matching record still showed its field; the same shape exists in a shared form.

### WP-071 Edit or create a form through the design API alone, without the designer
**Rule:** Read the live design object from `GET DAPI user-management/get-app-data-for-design/{client}/{app}/{userId}` (`Result.EntityTypes[]`, userId = the token's `sub`), back it up, change it, and send it to `POST DAPI EntityType/SaveEntityType` with `IsEdit: true`, `ParentSchemas: []`, `ChildSchemas: []` and the raw live `Version`. Use this only for forms with no parent or child relations (`Result.ParentChildRelations`): the body has no real `ChildSchemas`, so a save with `ChildSchemas: []` may drop a child link. A form's buttons (`CustomActionsConfiguration`) are in the design object once it has some and pass through the save unchanged (WP-072). Add a field by cloning a field **of the same form** (replace its `Name` everywhere, set `Label`, `Hint`, sequence and the matching `*FieldLastIndex`), then change `ControlType`/`DataType` if you need another type. A new form: copy another form's design object, give it new `EntityTypeID` and `GlobalTypeID` GUIDs, `Tittle`, `IsEdit: false`, `Version: "0"`, `EntitityXML: ""` (the server rebuilds the layout XML from `AllFields` on every save), keep only a section (ControlType 9), a column (8), your fields and the system fields (99), reset every `*FieldLastIndex`, then call `POST DAPI EntityType/SaveRolePrivilegeForEntityTypes` `{EntityTypeID, PrivilegeCodes:32655, RoleID}` with the admin role from `Result.Role`. Read the object back after each save and check every field is there.
**Why:** It needs no browser capture, keeps record data (dropdown and field changes left all records in place), and the server keeps the layout consistent.
**Caveats:** On a brand-new form, a field cloned from another form was dropped from the save without an error; adding it in a second save, cloned from the new form's own field, worked. After a field was added to a new form, the first workflow run read that field as empty although the record held a value; the next run read it correctly. Guard any value a workflow reads from a just-added field (a floor or default) and test twice. Dropdown choices: key = label (WP-043); changing existing keys needs the WP-061 conversion.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: three existing forms edited (choices added and converted, three date fields and a Yes/No field added) with record counts unchanged; one new form created, given privileges and filled; its integer field read as empty in the first run (ticket numbers 1 to 3) and correctly in the second (200010).

  - Design-format fields for child forms are also in `GET DAPI user-management/get-app-data-for-design/{client}/{app}/{userId}` → `Result.EventTypes[].AllFields` (top-level in `EntityTypes`).
- `POST DAPI EntityType/DeleteEntityType` body `{entityType:<full design object>, LiAnalyticsSetting:null}`; simplest is the designer's **Delete This Form** menu, guarded by a route that checks the form ID.

## 5. Relations, privileges, menus

- `POST DAPI EntityType/SaveParentChildRelations` body `{parentId, childIds:[...], appId, ClientId:<number>, SchemaMode:0}` → **adds** the listed children (existing ones stay).
- `POST DAPI EntityType/SaveRolePrivilegeForEntityTypes` body `{EntityTypeID, PrivilegeCodes:32655, RoleID}` → what the designer does for the admin role when a form is created.
- `POST DAPI Settings/GetAllDynamicMenuItems` body `{ClientID, AppId}` → design menu list.
- `POST DAPI Settings/SaveDynamicMenuItem` body = a menu item. **Set `Client.ClientID`, `Client.ClientIDString`, `Client.AppId`, `CloudApperAppId`** (the list returns ClientID 0). Update: existing `MenuID` + `IsEdit:true`. Create: generate a new GUID `MenuID` with `IsEdit:false` (an empty MenuID returns 204 and creates nothing).
- `POST DAPI Settings/DeleteMenuItem` body = the menu item (with real client) → `true`.
- Saved list views: WP-073.

### WP-073 Create a saved list view through the API
**Rule:** List all views with `GET API v3/formviews/` (also in `GET API v3/Apps/{appId}/details` → `Result.FormViews`). Create one with `POST API v3/formviews/`: copy an existing view of the same form (its default "Primary View" gives the right `TypeId` and `MenuId`), **remove `Id`, `CreatedDate`, `CreatedBy`**, and set `Title`, `Description`, `DefaultView` (false unless it should replace the default), `ViewDefinition.Fields` (the columns in order, internal names such as `integerField1`), `ViewDefinition.FilterConfiguration` (the workflow-filter shape: `{Condition:"AND"|"OR", Rules:[{Field, Operator, Value, TypeId:<form id>} or nested {Condition, Rules}]}`) and `ViewDefinition.SortConfigurations`. `ViewType 1` = list. Who sees it: `PermissionType 2` = everyone; `PermissionType 1` with `FormViewPermissions:[{PermissionType:1, PermittedId:<user id>}]` = those users. The response returns the new view with its `Id`; read the list back.
**Why:** It is the call the web app itself makes (`SaveFormView` → POST to the formviews controller), so a view built this way behaves like one saved in the app, without driving the UI.
**Menus with their own views:** a view belongs to one menu item (`MenuId`). To give users a new navigation entry (for example tabs of a planned screen), create the menu items first with `POST DAPI Settings/SaveDynamicMenuItem` (a group: copy an existing group, `Type 0`, `TypeID "0"`, `Level 1`; a list entry: copy an existing form list item, `Type 1`, `TypeID` = form id, `Mode 2`, `Level 2`, `ParentID` = group, `IsListView` and `IsMobileView` true, `ViewType 1`; new GUID `MenuID`, `IsEdit:false`, real client in `Client` and `CloudApperAppId`, empty `FilterConfiguration`/`SortConfiguration`), then create the views with `MenuId` = the new item, **including one with `DefaultView:true` per item**: a new menu item starts with no views at all. Several menu items can point at the same form with different views.
**Caveats:** Filter values are stored values (dropdown keys, WP-061). An "Open" view is a filter (several statuses with OR), not a status; integer filters with `>=` work. The `SortConfigurations` format is not known yet (every view seen had `[]`), so views built this way have no sort. Updating an existing view (POST with its `Id`) and deleting one were not tested. Back up the view list and the menu list (GetAllDynamicMenuItems) before changing them; users see new menus after **Reload App**.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: an "Open Tickets" view (8 columns, OR filter on three statuses, everyone) created with one POST without an Id; then a new menu group with four items over two forms and 11 views (status filters, a `>=` level filter, one default per item), all created through the API and confirmed by the owner in the app after Reload App.

- **Three menu levels work:** a group (Level 1) can hold groups (Level 2, `ParentID` = the top group) that hold form items (Level 3). Move an item by saving it with a new `ParentID`, `Level` and `SequenceNo` (`IsEdit:true`); set `Level` on the children too. A list item can sit at Level 1 with `ParentID: ""`. Clean up the auto-created per-form groups ("<Form>" with an "Add <Form>" item, made when each form is created) by saving them with `Ishidden:true` rather than deleting: it is reversible and the forms stay reachable from list menus, buttons and UI workflows. Checked 2026-11: four list items moved to Level 1, seven groups nested under a new top group, 48 items hidden, confirmed by the owner after Reload App.
- Regroup / rename / reorder / re-icon menus: save each existing item with changed `Title`, `ParentID` + `Level` (1 top, 2 child), `SequenceNo`, `IconURL` (reuse an URL from another menu, or upload a new icon through the files API, WP-079), `Ishidden`, and `PermissionType` + `Permissions` (copy from a restricted group to restrict a group). Read back with GetAllDynamicMenuItems; runtime `Apps/{app}/details` `Menus` updates at once, but open browsers show the cached menu until **Reload App** (↻ next to the app name, about x=222, y=22 at 1920×1080) is clicked. Start page = the menu item with `IsLandingPageMenu: true` (set it on the new one, false on the old). Back up all menu items (GetAllDynamicMenuItems) before changing any, so the menu can be restored exactly.

### WP-079 Give a menu a new icon through the API (upload, then IconURL)
**Rule:** Upload the image with `POST <cluster>-api.cloudapper.com/api/v2/Files/upload` (runtime auth headers, as `ca.js`, but no JSON content type): a multipart form with `UploadedFile` (the PNG, with its file name) and `FileInfo` (a JSON part named `Info`: `{"OriginalFileName","FileExtension":".png","FileSizeInKB","FileType":"image/png"}`; the designer sends the byte count in `FileSizeInKB`). Take `Result.OriginalURL` (the platform file repository, `.../0/default/<id>.png?CloudFileType=0&OriginalFileName=<name>`), GET it to confirm it serves the image, back up `GetAllDynamicMenuItems`, then save the menu item with that `IconURL` (`Settings/SaveDynamicMenuItem`, `IsEdit:true`, client fields set). Users see it after **Reload App**.
**Why:** The designer's icon picker ("Browser" opens the platform icon library, which has an image upload) stores the file with this same call and only then puts its URL on the menu; the menu save itself carries just the URL.
**Caveats:** Found by blocking all non-GET requests in the menu designer, attaching the file and recording the request, then cancelling (nothing saved); repeat that capture if the call changes. Uploaded files stay in the repository when a menu is changed back. Third-party icons (Flaticon and similar) need the author credit their license requires; download the PNG from the icon CDN by ID, do not hotlink it as the `IconURL`.
**Status:** Observed · checked 2026-11 · Studio 8.2.0 · Evidence: one 128 px PNG uploaded through the API (HTTP 200, the returned URL served image/png with the original size), set as a list menu's icon; read back with the new icon and unchanged title, level and parent.

## 6. UI workflows

- `GET API v2/Apps/ui-workflow-definition/{clientId}/{appId}` → `Result` = JSON string of the list.
- `PUT API v2/Configurations/update-app-configuration?config-to-update=Workflow` body `{AppId, ClientId, Configuration:[...full list...]}` → replaces the whole list (read, modify, write back).

### WP-076 Change a form's record title through the API
**Rule:** The record title (`DisplayName`) is built from the fields with a `DisplayNumber`, in that order (1, 2, ...). To change it, set `DisplayNumber` on those fields in the design object (`AllFields` and the matching `<Attribute ... DisplayNumber="n">` in `EntitityXML`), save with `EntityType/SaveEntityType` (WP-071 rules), and read back. Then update existing records: send `DisplayName` itself through `POST API v3/Records` in batches of 20 (WP-027), built the same way (field values joined by a space), and compare every record afterwards.
**Why:** Saving the form does not recompute titles of existing records, and re-saving a record without `DisplayName` keeps the old title; the app's own screens send the title with each save.
**Caveats:** Reference fields elsewhere keep the old display text until those records are saved again. Check whether records saved later by a workflow get the new title; if not, map `DisplayName` in that workflow too.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: Employees title changed from Person Number + Full Name to Full Name + Person Number; 474 records updated and read back with no mismatch.

### WP-078 Lay out a form in two desktop columns through the API
**Rule:** In the design object, a section is an `AllFields` entry with ControlType 9 (`GroupNumber`), each column an entry with ControlType 8 (`GroupNumber`, `ColumnNumber`), and each field has `GroupNumber`, `ColumnNumber`, `SequenceNumber` plus a `StyleSettings` JSON string whose `layoutConfigurations` hold one entry per platform (`platform:0` = desktop, with zero-based `SequenceNumber`; `platform:2` = phone). For two desktop columns: add a ControlType 8 entry with `ColumnNumber:2` per section (clone column 1), then place fields as rows of pairs: row k left = column 1, sequence k; right = column 2, sequence k; set the same values in the field and in its `platform:0` entry; leave `platform:2` alone so phones keep one column. Save with `EntityType/SaveEntityType` (WP-071); the server rebuilds `EntitityXML`. Read back and compare field counts.
**Why:** Columns stack independently, so pairing related fields row by row (Start | End, Code | Label, Name | Number) keeps them side by side; a gap in the middle of the right column shifts everything below it, so put unpaired fields at the end of their section.
**Caveats:** For a form with child (or parent) forms, send `ChildSchemas` / `ParentSchemas` as the full schema objects of those forms from `GET API v3/Apps/{appId}/details` → `Schemas` (ids from `ParentChildRelations`); that is what the designer sends. Then check the relations, the child records' `ParentId`, and any buttons (`CustomActionsConfiguration`) after the save. Keep the fields used for the record title (`DisplayNumber`) unchanged.
**Status:** Observed · checked 2026-11 · Studio 8.2.0.25 · Evidence: 17 forms laid out in pairs (2 with child forms: relations, child links and the form button kept), all fields kept on read-back; confirmed in the app on one form.
